Every file below is the file that deploys, imported at build time rather than pasted.
A copy that can drift is a copy that will, so a check in CI fails the moment what is
published here differs from what is in `terraform/`.

<Aside type="note" title="Why the configuration is imported rather than shown inline">
Pasted into a code fence, this configuration would be part of the page source, and the
page source is translated into twelve languages. The comments inside it would be
translated with it, and each locale would publish a different, wrong configuration.
Imported, it never enters the page source at all.
</Aside>

Dedicated AWS S3 backend; its configuration is supplied at init time and not
committed. The separate `terraform/bootstrap/state-backend` stack creates its
KMS-encrypted, versioned bucket and native lockfile support before the showcase
is initialized. It also configures server-access logging, EventBridge object
notifications, and an independently encrypted cross-region recovery replica.

### `terraform/kvm.tf`

Declarative KVM & libvirt infrastructure managed natively via `dmacvicar/libvirt`.
The network name and bridge are generated from the stable CE MAC/IP map; each CE
therefore receives the same reserved address after a replacement. The base volume
uses the F5-issued KVM appliance URL from `xcsh_site_image`, never a generic cloud
OS image.

<Aside type="caution" title="KVM image resolution">
The pinned `xcsh` v15.0.3 provider resolves the appliance from exactly one Site UID
owned by the named Secure Mesh Site v2 configuration. It checks the exact UID response
from `/api/maurice/software_os_version`, the empty error status, HTTPS image URL,
MD5, and ownership again before use. Terraform captures that verified boot artifact for the
site generation. A later current-image response does not replace an ONLINE CE disk;
an explicit site replacement or destroy and rebuild selects a new artifact. An ambiguous owner or incomplete mapping stops
planning without a repair or overwrite shortcut. Keep `enable_kvm = false`
(the default) to omit KVM from an unrelated apply or to produce a KVM-only destroy
plan without querying the image endpoint.
</Aside>

### Recovering a deleted KVM CE

Terraform can recreate missing managed hardware while preserving the configured
site, MAC addresses, shared bridge and routing identities. Recreating hardware is
not a backup restore: if the writable disk was deleted, its guest-local contents
are lost. The retained verified base image and provider-issued cloud-init start a
new CE registration.

First distinguish an I/O pause, a missing domain definition and a deleted disk.
Inspect libvirt domain state and block errors, disk availability, Terraform state,
and the site's registration inventory. Reclaim verified disposable caches when
the host filesystem is full. Resume an I/O-paused guest after correcting storage;
do not replace its disk solely because it is paused.

For an externally deleted domain and disk:

1. Keep the exact reviewed source and private inputs, acquire the lifecycle lock,
   and verify backend, site and disk ownership. Preserve shared bridge/uplink and
   host management.
2. Create a saved targeted plan for `libvirt_domain.ce_node` in the hardware phase.
   Keep the full deployment inputs and source identity; the target includes its
   dependencies. Review every action before applying the exact saved plan.
3. When only the CE domain, writable disk and cloud-init ISO are missing, require
   those three creates and no unrelated cloud, site or shared-network mutation.
   If the plan includes another action, investigate it before applying.
4. Wait for the replacement registration to become ONLINE. A valid site-bound JWT
   may permit enrollment under the existing site, but successful VM creation does
   not establish registration or routing health.
5. Return to a full refresh-enabled plan in the configured phase. Reconcile the
   new runtime hostname, MAC-owned SLO/SLI and BGP references through Terraform.
   XC may retain terminal registrations and old platform children; these must
   remain distinct from the exact live replacement. A missing or ambiguous
   identity remains a failure.
6. Verify static SLI readback, one Established FRR session, the expected route,
   private DNS and exact-origin VIP traffic from the independent physical client.
   Require preserved management/default routes and a final refresh-enabled
   zero-change plan with every showcase path enabled.

A saved targeted plan is an exceptional recovery step, not completion evidence.
The final full plan must converge. Never remove stale runtime adoption from state
without exact ownership and replacement evidence, and never delete an
XC-owned child directly to force a successful plan. A provider or API contract
rejection belongs in its owning repository; deliver and verify the repair before
claiming the recovery complete.

### When the retained site cannot recover

In a single-node KVM recovery, the retained site can keep the deleted node's
terminal registration as **Control** and enroll the new runtime hostname as a
**Worker**, even with the original MAC addresses. The replacement may briefly
report ONLINE before heartbeats fail. Hardware creation and initial enrollment
therefore do not prove a working replacement Control node.

Inspect the owning site's node roles, registration states and guest bootstrap
logs. If the old Control remains terminal and the replacement cannot sustain
health, use an explicit teardown and rebuild of the owned KVM site and its
dependent CE hardware. Keep the full private inputs and lifecycle lock. Save a
destroy plan targeting `xcsh_securemesh_site_v2.onprem_kvm`, inspect its dependency
closure, and require only owned KVM site, token, boot-image, hardware, runtime
adoption and dependent routing/demo objects. Preserve the shared bridge/uplink,
host management, backend bootstrap and all unrelated cloud resources.

The runtime-interface resource must restore DHCP through the owning site's
versioned update route before the site is deleted. A terminal predecessor still
requires exact site UID, child ownership, hostname, device, MAC and saved static
address checks. If the published provider rejects that teardown, stop and deliver
the provider repair; do not delete the platform child or remove adoption state
to bypass the error.

After applying the reviewed destroy plan, prove the old site and owned hardware
are absent. Rebuild through Terraform's hardware phase, verify a fresh
single-Control-node registration, then converge the configured phase. Repeat
the independent physical-client routing and exact-origin traffic checks above
and require a full refresh-enabled zero-change plan. This is an explicit site
generation change; ordinary repeat plans must preserve the boot disk and VM.

The owned-site rebuild was verified after the retained-site replacement failed:
the fresh site enrolled exactly one ONLINE Control node, adopted its static SLI
through the owning-site update, established FRR routing and served ten
exact-origin VIP requests from the independent physical client. The shared
bridge, uplink and default routes remained intact. The full refreshed plan then
reported no resource or output changes. Keep these as acceptance gates for every
recovery; an earlier successful run does not establish a new deployment's health.
